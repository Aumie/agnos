# Decision Log — Hospital Middleware

A running list of the non-obvious decisions made while building this, and the reasoning behind each — so the "why" behind the code isn't lost to history.

## Architecture

- **Package-by-feature, not layer-by-layer.** Rejected an initial Clean-Architecture-style `domain/usecase/adapter` split (too C#/.NET-flavored) in favor of idiomatic Go: each package (`patient`, `staff`) owns its struct, its logic, and the interfaces it needs.
- **Interfaces defined at point of consumption, always.** No central `ports`/`contracts` package. One violation of this rule got caught mid-build: `event.Publisher` was originally defined in `event` (the implementer's package) instead of `patient` (the consumer) — moved it, which also removed the need for a generic `Event` marker type, since there's only ever one concrete event.
- **No DI container.** Manual wiring in `main.go` — explicit, greppable, matches how the rest of Go's ecosystem does it (unlike .NET's `IServiceCollection` culture).
- **`postgres` is one package implementing multiple domain repositories**, not a repo-per-folder tree — avoids C#-style folder explosion for what's structurally a small schema.
- **HIS adapters are multi-hospital-ready even though only Hospital A is specified** — the scope frames the system as talking to "Hospital Information Systems" (plural), and a middleware whose whole point is HIS-agnosticism shouldn't be hardcoded to one.
- **Rejected MediatR-style mediator/pipeline abstraction.** Not idiomatic Go — Go favors explicit direct calls over DI-container-discovered handlers; the traceability cost (can't just "go to definition" through a mediator) isn't worth what MediatR buys.
- **Rejected Elasticsearch, Watermill, NATS, a message broker, microservices** — all considered and deferred as "next tier if this ever needed to scale," not built. `pg_trgm` is the noted future upgrade for fuzzy name search; a real broker is the noted future upgrade for the event bus. Neither is needed at this scale, and building either now would be solving a problem that doesn't exist yet.

## Data model / API contract

- **Added a `hospitals` table** beyond the two schemas the scope names (Patient, Staff) — needed as an FK target for referential-integrity-backed hospital scoping, and to give the `his` registry a stable `code` routing key decoupled from the human-readable `name`.
- **`hospital_id` (FK, internal) vs `hospital` (API string) kept distinct** — the API-facing `hospital` field is always the *code*, never conflated with the display name.
- **Removed `hospital_name`/`hospital_code` from API responses entirely** after re-checking the scope text — it specifies no such output field (Hospital A's response has no hospital field at all, and the search task doesn't ask for one). `/staff/create` just echoes back the submitted code.
- **Username uniqueness is per-hospital, not global** — two hospitals can each have their own `nurse_j`. Why `hospital` is required on both `/staff/create` and `/staff/login`.
- **`/staff/create` left unauthenticated** for this scope (no role/admin concept given) — flagged explicitly as a production gap, not left silent.
- **`/staff/refresh` added** beyond the literal task list — needed to back the short-lived-JWT + refresh-token design.
- **Pagination (`page`/`page_size`) added to `/patient/search`**, response wrapped in `{data, page, page_size, total}` rather than a bare array — an all-empty-filter request means "every patient in my hospital," so pagination is a safeguard, not scope creep.
- **POST used for all 4 self-implemented endpoints** — the scope specifies a verb only for Hospital A's *external* API (GET); all 4 of the endpoints being implemented here take JSON bodies, and POST is the only sane choice for that.
- **Name search is language-agnostic**: `first_name`/`middle_name`/`last_name` (no `_th`/`_en` split in the request) match against *both* stored columns, OR'd — since the search input has no way to specify which language, and staff shouldn't need to know which one's on file.
- **Local Postgres, not a live pass-through, is what `/patient/search` actually queries.** Hospital A's API only supports lookup-by-id — it has no capability to filter by name/DOB/phone/email at all, so those filters could never work as a pure proxy. Postgres becomes the searchable store, synced on id-lookup.
- **Graceful degrade when a hospital exists in the DB but has no registered HIS adapter** (`his.Registry`) — distinct code path from "HIS has no match," logged server-side, never surfaced as a request error. Realistic scenario: a hospital onboarded administratively before its integration is coded — concretely, that means via a migration or a manual `INSERT`, since there's no hospital-management API; see `api-spec.md`'s Assumption 7, added after this was asked about directly and turned out to be unstated anywhere in the three planning docs.
- **`patient_hn` given a real uniqueness constraint** (`NOT NULL`, unique per hospital) — caught as a gap during a later recheck; it's the hospital's own identifier and should behave like one.
- **`RefreshTokenExpiresAt` added** — caught as a gap: a refresh token hash with no accompanying expiry is unenforceable, and the API spec already committed to a 7-day lifetime.
- **`openapi.yaml`'s `servers: /api/v1` prefix was a real bug**, silently contradicting the scope's literal route paths (`/staff/create`, not `/api/v1/staff/create`) — found on a full recheck against the scope text, fixed.

## Auth / security

- **JWT access token (15 min) + opaque refresh token (7 days), single active refresh token per staff row** — no rotation/blacklist infrastructure, explicit simplification.
- **JWT claims carry both `staff_id` and `hospital_id`** — avoids a DB round-trip per request for hospital scoping. Accepted staleness risk is moot because nothing in scope ever reassigns a staff member's hospital.
- **Refresh token is a random opaque value, not a JWT** — it's always DB-verified anyway (every refresh hits the DB to check + rotate), so there's no benefit to it being self-describing, and one fewer place for an algorithm-confusion bug to live.
- **Refresh token hashed with SHA-256, not bcrypt** — it's already high-entropy (32 random bytes), unlike a human password; bcrypt's slowness protects against brute-forcing *low*-entropy secrets, which doesn't apply here.
- **Password length bounded 10–20 characters** — max specifically chosen to sit well under bcrypt's 72-byte silent-truncation limit (avoids two different long passwords hashing identically).
- **`Login` always performs exactly one bcrypt comparison, regardless of which lookup failed** (unknown hospital / unknown username / wrong password all take the same-cost path via a precomputed dummy hash) — closes a timing side-channel that would otherwise let an attacker enumerate valid usernames via response latency, even with an identical error message.
- **Publish failures for any of the 8 events never fail the request that triggered them** (`SyncedEvent`/`SyncFailedEvent` in `patient`, all 6 `staff` events) — a bug in the optional audit/event side-feature must not be able to break a required, graded endpoint. Each publish call is wrapped by a small `publishX` helper that logs and swallows the error; the original result/error from the actual operation is what propagates.
- **Hospital A's "not found" behavior assumed to be HTTP 404** — the scope specifies Hospital A's response body but not its status-code contract for a miss; 404 is the REST convention, and `/mockserver` must match this exactly.
- **`id` sent to Hospital A is URL-escaped** (`url.PathEscape`) — passport IDs aren't guaranteed numeric-only, unlike national IDs; unescaped, a stray `/` or `?` could alter the request path.

## Testing

- **Hand-written fakes over `gomock`** — every interface here is 1–4 methods; fakes need no codegen step, behave statefully (closer to real DB semantics — e.g. create-then-find round-trips actually work), and are as readable as any other Go code. `gomock` earns its keep on much larger interfaces or heavy call-sequence assertions, neither of which applies here.
- **`event.Bus[T]` built with generics**, not a shared `Event` marker interface — preserves "interface owned by consumer" even as more event types get added later; each domain package's own `EventPublisher` interface is satisfied structurally, no shared marker type needed.
- **Additional event types (`CreatedEvent`, `LoginFailedEvent`, etc.) deliberately deferred**, not defined ahead of the service methods that would publish them — defining them earlier means events with no publisher and no subscriber, which is worse dead code than having just the one event.
- **`/event` + `/audit` sequenced to be built last**, and would have been the first thing cut if time had run short — it demonstrates how this could evolve toward an event-driven/microservices split without over-building the current scope, and isn't required by any task in the scope. Time allowed for it, so it was finished rather than left as scaffolding: all 8 events now have a real fire site, a real subscriber (`internal/audit`), and a dedicated test.
- **`internal/audit` is 8 plain functions, not a struct/interface, and each is a closure over `*log.Logger`** (`func LogSynced(logger *log.Logger) func(context.Context, patient.SyncedEvent) error`) — a subscriber only needs to satisfy `event.Subscriber[T]` (a bare function type), so there's no reason to wrap it in a type with one method. The closure is what lets `main.go` pass the same shared `logger` to all 8 without a struct field for it.
- **`main.go`'s manual `EventPublishers{...}` struct literals (one field per event, 8 total across `patient`/`staff`) can't be pushed into `staff`/`patient` themselves or replaced with a loop.** Asked directly whether there's a better way as the event count grows. Can't move the wiring into `staff`/`patient`: `internal/audit` already imports both, so either package owning a "default wiring" helper that calls into `audit` would create `staff → audit → staff` — the same import-cycle shape `hospital`/`his` hit earlier. `main.go` is the only package allowed to see both ends. Can't loop either: each event is a distinct Go type, so `event.Bus[T]` is a different concrete type per event — no runtime iteration over "all event types" without reflection/codegen, which would reopen the same reflection-vs-explicit-map tradeoff already decided against for the HIS adapter registry.
  - **Real gap found in the process, and fixed: a struct literal with named fields doesn't require every field to be set.** A forgotten field silently compiles to a nil interface, and only panics the first time *that specific event* fires (`nil.Publish(...)`) — for a rare path like `RefreshFailed`, that could go unnoticed for a long time, and gets more likely to happen as the event count grows. Added `event.RequireComplete(bundle any)` (`internal/event/validate.go`, small reflection helper), called once inside `staff.NewService`/`patient.NewService`, so an incomplete bundle panics immediately at construction — loud and at startup, not silent and at first use of one specific path. This is a safety net on top of the existing explicit wiring, not a replacement for it — still no DI container, still no auto-discovery.
- **`event.NewBusWithSubscriber[T](fn)` added as a convenience constructor** (`NewBus[T]()` + one `Subscribe` call) — every real use in `main.go` immediately subscribes exactly one thing (`/audit`'s logger) right after creating the bus, so this collapses that two-line pattern repeated 8 times in `main.go` into one call each, without adding any behavior `NewBus`+`Subscribe` didn't already have.

## Tooling / infra

- **`go.mod` pinned deliberately, not left to drift.** `x/crypto`/Gin's latest wanted `go 1.26`, which would've pulled in a toolchain newer than what's actually installed locally — repinned dependency versions to keep `go.mod` matching the installed Go version, since an unexpected toolchain bump is a real risk for the Docker build later (the base image needs to match or exceed it).
- **`pgx/v5` directly, no `sqlx`, no ORM** — Postgres-only project, so no need for a driver-agnostic layer; `pgx.CollectRows`/`RowToStructByName` give struct scanning without needing `sqlx` on top. Row structs (`patientRow`, `staffRow`, `hospitalRow`) stay separate from the domain types, same anti-corruption-layer pattern used for Hospital A's wire struct — the domain types never carry `db` tags.
- **`golang-migrate`, run as a one-shot `docker-compose` service** — `migrate/migrate`'s official image, invoked before the API container starts (`depends_on: condition: service_completed_successfully`), so `docker-compose up` alone gets a fully migrated database with no manual step.
- **A seed migration (`000002_seed_hospitals`) is separate from the schema migration (`000001_init`)** — keeps DDL and reference data apart, but was necessary either way: without seeding `hospital_a`, a fresh database has zero hospitals and `/staff/create` fails immediately for every request.
- **One `Dockerfile`, two named build targets (`api`, `mockserver`), not two separate Dockerfiles** — both binaries share one builder stage; `docker-compose.yml` picks the target per service via `build.target`.
- **`his.NewDefaultRegistry(his.Config{...})` replaces explicit `.Register()` calls in `main.go`** — as more hospitals get onboarded, `main.go` shouldn't accumulate one `.Register()` line per hospital; that list belongs in `his` (the package actually about hospital integrations), not the composition root. `his.Config` is its own small struct (just the base URLs adapters need), not the app-wide `config.Config`, so `his` doesn't gain a dependency on the top-level config package — `main.go` maps the one field it needs across. `NewRegistry()`/`Register()` stay exported as the lower-level primitives (still used directly in tests to build ad-hoc registries with 0 or 1 clients).
- **Each hospital's adapter gets its own subpackage under `his/`** (`internal/his/hospitala`, a future `internal/his/hospitalb`, etc.), **named after the hospital, not `hospital`** — a first attempt at this used the directory/package name `hospital`, which silently collides with the pre-existing `internal/hospital` package (the shared Hospital entity). Go allows two different import paths to have the same package name, but anything needing both would need an import alias, and it reads as confusing regardless. `hospitala` is unambiguous and scales cleanly to `hospitalb`, `hospitalc`, etc.
- **`his.LoadConfig()` reads hospital-specific env vars (`BASE_URL_HOSPITAL_A`, etc.) directly — `internal/config` doesn't know they exist.** Originally `internal/config.Config` had a `HospitalBaseURL` field, and `main.go` manually copied it into a separate `his.Config`. That's duplicative for one hospital and gets worse linearly with each new one — three places to touch (the generic config struct, `his`'s own struct, and the copy-line in `main.go`) for something that should be one. This was actually inconsistent with a decision already made: `his.Config` was deliberately kept separate from `config.Config` specifically so `his` wouldn't depend on the top-level config package — but the *sourcing* of the values still lived in the wrong package. Fixed by giving `his` its own `LoadConfig()` (mirroring `internal/config`'s own `getEnv` helper, duplicated rather than shared — three lines isn't worth a shared package). `internal/config` now only owns genuinely generic, app-wide values (`PORT`, `DATABASE_URL`, `JWT_SECRET`); `main.go` is just `his.NewDefaultRegistry(his.LoadConfig())`, no manual field mapping. Adding a hospital now touches exactly one file (`internal/his/adapters.go`), not three.
- **`StaffRepo.Create` translates a Postgres unique-violation (`23505`) into `staff.ErrUsernameTaken`**, on top of the service-level pre-check — the pre-check alone leaves a race window between check and insert; the DB constraint is the actual authoritative guard, so the translation makes sure that race still produces the right 409, not a raw 500.
- **`internal/postgres` was originally written without local execution verification** — no Docker was available during that phase. Since resolved: see "End-to-end verification" below for the integration tests and full docker-compose run that confirmed it (and caught a real test-isolation bug in the process).
- **No DB-swap abstraction beyond the interfaces already in place.** The scope mandates Postgres by name; `patient.Repository`/`staff.Repository` are already swappable as a unit (consumer-owned interfaces), which is sufficient — going further (dialect-portable SQL, a query builder) would mean not using Postgres-specific features (partial unique indexes, `ON CONFLICT ON CONSTRAINT`) that are the *correct* tool for a database the scope isn't going to change.
- **`internal/hospital` must stay its own leaf package — tried moving `Hospital` into `his` once, reverted.** `his` already has to import `patient` (to implement `patient.HISClient`/`HISRegistry`, the consumer-owned interfaces). If `Hospital` also lived in `his`, `patient` would need to import `his` back (for `his.Hospital` in its own `HospitalLookup` interface) — `patient → his → patient`, a hard compile error in Go, not a style problem. Only a package with zero dependencies on either side can be shared by both, which is exactly why this was a separate leaf package from the start. Worth remembering before attempting this move again.
- **`hospitala`'s exported type is `Client`/`NewClient`, not `HospitalAClient`/`NewHospitalAClient`.** Caught on a full recheck: the constructor had been shortened to `NewHospitalClient` but the type it returned was still `HospitalAClient` — `NewX` not returning `*X` is a real Go-convention break, not just a style nit. Since the package is already named `hospitala`, the type name doesn't need to repeat "Hospital A" at all — `hospitala.Client`/`hospitala.NewClient(...)` says everything the qualified name needs to, same pattern many Go API client packages use (package name disambiguates, type is just `Client`).
- **Considered, built, then reverted `init()`-based self-registration for hospital adapters — ended up on an explicit map instead.** Worth keeping the full arc, not just the ending, since the reasoning at each step is the actually useful part.
  - **Why a plain loop alone was never enough:** nothing tells a loop *which Go constructor* to call for a given hospital code, since every adapter is bespoke, hand-written parsing code — the wiring step is irreducibly manual no matter how the surrounding code is shaped.
  - **First built: `his.FactoryRegistry` + a global `DefaultFactories` + each hospital package self-registering via its own `init()`** — the same pattern `database/sql` uses for drivers. Real, working code, deliberately built despite an initial recommendation against it, specifically because working code was wanted over a documented-only answer.
  - **Then reverted, on a direct question ("so a plain explicit map is better?") that was worth answering honestly rather than defending the sunk work.** The `init()` approach's real cost: it only runs if something blank-imports the package for the side effect (`_ "internal/his/hospitala"`) — that dependency doesn't disappear, it becomes invisible, sitting in an import list far from the code that relies on it, with a *silent* failure mode (missing the import = hospital never registered, no compile error). That's exactly the implicit wiring this project ruled out from the start ("no DI container, everything wired by hand, explicit and greppable"). `database/sql` needs `init()` because it's a stdlib package that can't know about third-party drivers ahead of time; this codebase owns every adapter it will ever have, so it doesn't have that constraint — explicit registration costs nothing extra by comparison, and reads better: to see every hospital this system supports, open one file (`adapters.go`'s `adapters` map) and read it top to bottom, rather than tracing blank imports into scattered `init()` functions.
  - **Confirmed via a direct scale question ("100 hospitals = 100 blank imports?")** — yes, and that's inherent to Go (no true dynamic loading without the fragile, Linux-only `plugin` package), which is what surfaced that *both* approaches need N lines somewhere regardless — so the choice was never "avoid listing every hospital," only "which form does that unavoidable list take." The explicit map wins that comparison: same line count as N blank imports, but visible, no hidden execution, and a duplicate hospital code is a **compile-time** error (`go vet` catches duplicate map-literal keys) instead of a runtime `panic`.
  - **What survived from the `init()` attempt:** `Config` as `map[string]string` (code -> base URL), and the "100 hospitals" proof — now `TestBuildRegistry_ScalesTo100Hospitals`, registering 100 synthetic factories against `BuildRegistry` directly (a plain function, not an instantiable `FactoryRegistry` type — that ceremony existed only to keep `init()`-driven global state testable in isolation, and stopped being needed once registration went back to being a plain, non-global map literal).

## Docs / dev experience

- **Added a live `/docs` Swagger UI route**, serving the same `openapi.yaml` already written as a planning deliverable — no second copy of the spec. `docs/embed.go` (`package docs`, `//go:embed openapi.yaml`) embeds it at `go build` time, so the Dockerfile needed zero changes and there's exactly one source of truth for the spec, used both as a static planning doc and as the live page's data.
- **Swagger UI itself is loaded from a CDN in `internal/httpapi/docs.go`'s `swaggerUIHTML` const**, not vendored — it's a dev-convenience route, not a production requirement of the scope, so pulling the JS/CSS from a CDN keeps the binary and repo free of a vendored frontend bundle for something this peripheral.
- **Found and fixed a second real bug: every error response in `openapi.yaml` showed the same example (`INVALID_CREDENTIALS` / "username or password is incorrect") in Swagger UI, regardless of which status code or endpoint you were looking at.** The actual API correctly returns distinct codes per situation (`VALIDATION_ERROR`, `USERNAME_TAKEN`, `UNKNOWN_HOSPITAL`, `INVALID_CREDENTIALS`, `INVALID_REFRESH_TOKEN`, `UNAUTHENTICATED` — see `internal/httpapi/staff_handler.go`'s `respondStaffError` and `internal/httpapi/middleware.go`), but every response in the spec just did `$ref: '#/components/schemas/Error'` with no override, so they all inherited that one schema-level example. Fixed by adding a response-specific `example` (or `examples`, for `/patient/search`'s 401, which has two distinct causes) to every response that returns `Error` — `/staff/create`'s 409/422, `/staff/login`'s 401, `/staff/refresh`'s 401, `/patient/search`'s 401, and the shared `ValidationError` component used by every endpoint's 400. `/staff/login`'s 401 also got an explicit description explaining *why* it's one shared code across three causes, cross-referencing this file's Auth/security section, so the collapsed-error-code behavior reads as an intentional API contract in the spec, not an oversight. Verified visually in the browser against the rebuilt live stack.
- **Found and fixed a real bug: the `/docs` page had no way to enter a Bearer token.** `openapi.yaml`'s `bearerAuth` securityScheme and `/patient/search`'s `security: [bearerAuth: []]` were always correct, but `swaggerUIHTML`'s `SwaggerUIBundle(...)` init only passed `url`/`dom_id` — without `presets: [SwaggerUIBundle.presets.apis, SwaggerUIStandalonePreset]` and `layout: 'StandaloneLayout'`, Swagger UI silently renders with its default `BaseLayout`, which never shows the "Authorize" button/padlock at all, regardless of how correct the spec's security schemes are. Fixed by loading `swagger-ui-standalone-preset.js` alongside the existing bundle script and passing the standard `presets`/`plugins`/`layout` config swagger-ui-dist's own docs use. Verified visually in a real browser against the running `docker-compose` stack (Authorize button appears, click opens a token-entry field for `bearerAuth`) — the earlier `TestDocs_SwaggerUIPage` test only checked the page loaded and mentioned `swagger-ui`, which passed the whole time despite this being broken; the test now also asserts on `swagger-ui-standalone-preset.js` and `StandaloneLayout` specifically so this can't regress silently again.
- **README.md added at repo root** — tech stack, links to the three planning docs, `make up`/`down`/`logs`, a `go run ./cmd/api` fallback for running without Docker, testing instructions, the 4-endpoint API table, and an "Adding a second hospital" walkthrough pointing at the `internal/his/hospitala` pattern and the `adapters` map in `internal/his/adapters.go`.

## Input validation

- **`staff.Service` trims and length-bounds `username`/`hospital` code** (`MaxUsernameLength`/`MaxHospitalCodeLength`, 50 chars each) in both `CreateStaff` and `Login` — both are unbounded `text` columns with no DB-level cap, so without this a client could submit an arbitrarily large value. Login's over-length check runs before the hospital/username lookup, deliberately not the dummy-bcrypt-comparison path — an over-length value can never match a real row (bounded at write time by `CreateStaff`), so short-circuiting here leaks no more than the existing `ErrValidation`/`ErrInvalidCredentials` split already does.
- **`/patient/search`'s optional filter fields are trimmed and empty-string-normalized to nil, and length-capped at 200 chars**, in the `httpapi` handler (`normalizeSearchField`) — found a real bug while doing this: `"national_id": ""` wasn't being treated as "not provided" before this, so it would still trigger a live HIS sync attempt with an empty id (`syncCandidateID` only checks for a non-nil pointer). Fixed at the HTTP boundary, same layer that already handles `date_of_birth` format validation.
- **No app-level request body size cap added** — nginx's default `client_max_body_size` (1MB) already bounds it at the layer in front of the API; adding a second, redundant limit inside the Go handler wasn't worth the duplication.
- **Found and fixed a real bug on a later recheck: `/staff/create`'s response echoed the raw, untrimmed `hospital` field.** When `staff.Service.CreateStaff` gained input trimming, `createStaffResponse.Username` was already sourced from the service's return value (`created.Username`, correctly trimmed), but `Hospital` was still built from `req.Hospital` directly in the handler — `Staff` has no hospital-code field to read back (only `HospitalID`, a UUID), so the handler had never been updated when trimming landed. A client submitting `"hospital": "  hospital_a  "` got a staff row correctly linked to `hospital_a`, but a response with the whitespace still in it — silently inconsistent with the now-trimmed `username` field in the same response. Fixed by trimming `req.Hospital` in the handler before echoing it, matching what the service already validated against.

## Edge cases and concurrency

An explicit audit pass for edge cases beyond api-spec.md's required test list, on request ("any edge cases left, or anything I might miss"). Three were real gaps, fixed with tests; the rest are documented as intentional in api-spec.md's new "Known limitations" section rather than fixed, since they're scope/behavior decisions, not bugs.

- **Found and fixed a real gap: a malformed HIS response could reach an unhandled DB constraint violation instead of the already-graceful "genuine sync failure" path.** `hospitalAResponse.toDomain()` accepted any non-empty `gender` string and any (including empty) required name field with zero validation, but `patients.gender` has `CHECK (gender IN ('M','F'))` and `first_name_th`/`last_name_th`/`first_name_en`/`last_name_en`/`patient_hn` are all `NOT NULL`. A HIS response violating either would previously succeed through `SearchByID`, then fail at `Upsert` — which, unlike `SearchByID`'s own error path, never publishes `SyncFailedEvent`, so the failure would surface as a bare, unaudited 500. Fixed by validating both in `toDomain()`, so a bad response fails at the same point, and through the same already-tested-and-audited path, as any other "the HIS integration is flaky" error.
- **Found and fixed a real gap: `ILIKE` search values weren't escaped**, so `%` and `_` in a name filter were live SQL wildcards rather than literal characters — `first_name: "%"` matched every patient, `first_name: "_aidee"` matched any single character + "aidee". Not a SQL-injection risk (already parameterized), but a correctness one. Fixed with `escapeLikePattern` (`internal/postgres/patient_repo.go`) — escapes `\`, `%`, `_` before wrapping in `%...%`, relying on Postgres's default backslash escape character for `LIKE`/`ILIKE` (no `ESCAPE` clause needed).
- **Found and fixed a real concurrency bug: two simultaneous `/staff/refresh` calls presenting the same not-yet-rotated token could both succeed**, each minting a valid pair from a token meant to be single-use. The existing "replay of an already-rotated token" test only covers the *sequential* case (rotate, then reuse the old one — correctly rejected); it says nothing about two callers racing to consume the *same* token before either has rotated it. `RefreshToken`'s old shape — `FindByRefreshTokenHash` (read) then `UpdateRefreshToken` (unconditional write), as two separate statements — has exactly that TOCTOU gap. Fixed by replacing the plain write with `RotateRefreshToken`, a compare-and-swap (`UPDATE staff SET refresh_token_hash = $new ... WHERE id = $id AND refresh_token_hash = $old`): a single Postgres statement is atomic per-row, so of any number of concurrent callers racing on the same `oldHash`, exactly one can see `RowsAffected() == 1`; the rest get `ok=false`, which `RefreshToken` treats identically to a sequential replay (`ErrInvalidRefreshToken`). `Login`'s unconditional `UpdateRefreshToken` is unchanged — a fresh login isn't consuming an existing token, so there's nothing to compare against, and racing logins overwriting each other last-write-wins is fine. Proven at three levels: a fake-repo test with 20 real goroutines (`TestRefreshToken_ConcurrentUseOfSameToken_OnlyOneWins`), a real-Postgres test with 20 real goroutines hitting the actual `UPDATE...WHERE` (`TestStaffRepo_RotateRefreshToken_ConcurrentSameOldHash_OnlyOneWins`), and confirmed the same shape of race for `/staff/create` (two concurrent creates of the same username — the DB unique constraint already closes this, per the existing `23505`-translation code; added `TestCreateStaff_ConcurrentDuplicateUsername_OnlyOneWins` to actually exercise it concurrently rather than only sequentially) and for the patient-sync upsert (`TestPatientRepo_Upsert_ConcurrentSamePatientHN_NoDuplicateNoError`, 20 goroutines upserting the same `patient_hn` — `ON CONFLICT` already handles this, now proven under real concurrency).
- **`go test -race` isn't available in this environment** (`cgo` needs a C compiler; `gcc` isn't installed) — the concurrency tests above were run repeatedly (5-20x each) to check for flakiness instead of relying on the race detector, and the fakes they use (`fakeRepo` in `internal/staff`) were given their own mutex specifically so they're genuinely concurrency-safe, not just single-threaded-test-shaped.
- **Documented, not fixed, as intentional or out-of-scope** (api-spec.md's "Known limitations" section): no rate limiting/lockout on repeated failed logins, no CORS headers, `username`/`hospital` lookups are case-sensitive, `Content-Type` is never checked (Gin's `ShouldBindJSON` ignores it entirely — confirmed with `TestCreateStaff_HTTP_SucceedsWithoutContentTypeHeader`/`...WithWrongContentTypeHeader`). Also added `TestPatientRepo_Search_PageBeyondTotalResults` — a page number past the last page of real results was never explicitly pinned down as "empty data, correct total, no error" before, even though the SQL `LIMIT`/`OFFSET` already handles it correctly by construction.

## End-to-end verification (full docker-compose stack)

- **Confirmed the full stack works for real**: `docker compose up -d --build` (postgres → migrate → mockserver → api → nginx), then exercised every endpoint through Nginx on `:80` — `/staff/create`, `/staff/login`, `/staff/refresh`, `/patient/search` (both the empty-filter case and an id-based search that triggers a live HIS sync against `/mockserver`, confirmed via the `audit: patient synced` log line), plus `/docs` and `/docs/openapi.yaml`. `internal/postgres`'s integration tests (`hospital_repo_test.go`, `staff_repo_test.go`, `patient_repo_test.go`) all pass against the real container.
- **Found and fixed a real bug in the process: `go test ./...` was silently wiping the app's own seed data.** `internal/postgres`'s tests `TRUNCATE`d `hospitals`/`staff`/`patients` before every test, and defaulted to connecting to the same `hospital_middleware` database `docker-compose` seeds `hospital_a` into for real API traffic. Running the test suite against a live `make up` stack left `hospitals` empty, and `/staff/create` started failing with `UNKNOWN_HOSPITAL` — not a bug in the app, but a real gap in test isolation that would have bitten anyone running the obvious `make up && go test ./...` sequence.
  - **Fix: a second, dedicated `hospital_middleware_test` database, not unique-per-test hospital codes.** Considered making `seedHospital` generate collision-proof codes per test instead of relying on `TRUNCATE`-before-each-test for isolation, but ~18 call sites across 3 test files already assume a clean slate and a literal `"hospital_a"`/`"hospital_b"` — reworking all of them was a bigger, riskier change for the same outcome. A second database is one init script (`deployments/postgres/init/01-create-test-db.sql`, runs once via Postgres's own `docker-entrypoint-initdb.d`) plus one new one-shot compose service (`migrate-test`, mirroring `migrate` but targeting `hospital_middleware_test`) — existing tests didn't need to change at all, just `testDatabaseURL()`'s default.
  - **Caveat documented, not fixed further:** `go test` doesn't wait on `migrate-test`'s completion the way `api` does via `depends_on: condition: service_completed_successfully` in compose — running the test suite in the same instant as `docker compose up` (before `migrate-test` finishes) can race. Running it a few seconds later, or after confirming `docker compose ps` shows `migrate-test` exited 0, avoids this. Not worth solving with an app-level wait/retry for a take-home's test suite.
- **`hospital_b` seeded with its own migration (`000003_seed_hospital_b`) that inserts the hospital row *and* one patient directly** — not just the hospital, unlike a strict reading of "add a second hospital" (write the adapter package) would suggest. Reasoning: `hospital_b` has no HIS adapter (`internal/his/adapters.go`'s entry for it is still the commented-out example, not real code), so an id-based search for it hits the graceful-degrade path and finds nothing — there is no sync path that could ever populate a patient row for it. Seeding a patient directly is the only way `/patient/search` has something to actually find for a hospital_b-scoped staff member, and it makes `hospital_b` a live, running example of the graceful-degrade behavior (verified: searching an unseeded id for `hospital_b` logs `"no HIS adapter registered for hospital hospital_b, skipping live sync"` and still returns `200` with empty results, never an error) rather than a purely theoretical one. Verified end-to-end against the real stack: created a `hospital_b`-scoped staff member, logged in, confirmed search finds the seeded patient by name and by its seeded id, confirmed a `hospital_a`-scoped staff member's search for the same name returns nothing (tenant isolation holds).

## Deployment

- **Cloud Run for `api`/`mockserver`, Neon for Postgres — not Cloud SQL.** Cloud Run is a stateless compute platform by design: no durable local disk (writes vanish on restart/scale-to-zero), no guarantee only one instance of a container is running at a time (fatal for a single-writer database), and scale-to-zero itself (the thing that keeps it free) means a database would be shut down between requests. Cloud SQL has no perpetual free tier (only a 30-day trial), unlike Cloud Run's own free tier, which is real and ongoing. Neon's free Postgres tier is also perpetual and reachable over the public internet with no VPC/private-IP setup, which is what keeps this pairing simple — no networking work beyond a connection string.
- **`nginx` isn't part of the Cloud Run deploy path** — Cloud Run already terminates TLS and handles ingress/routing, which is `nginx.conf`'s only job in `docker-compose.yml`. `docker-compose.yml` itself is untouched; Cloud Run is an additional deploy path, not a replacement for local dev.
- **Migrations run once, directly, from `deploy-gcp.sh`** via the same `migrate/migrate` Docker image `docker-compose.yml` already uses, pointed at Neon's connection string — no new migration tooling, no Cloud Run Job needed for something that only needs to run once per schema change.
- **`mockserver` deployed first, `api` second** — `api`'s `BASE_URL_HOSPITAL_A` env var needs `mockserver`'s live Cloud Run URL, so the two can't deploy in parallel or in the other order without a placeholder-and-redeploy step.
- **`JWT_SECRET` generated fresh per deploy (`openssl rand -base64 32`), never the local dev placeholder** — the dev secret in `docker-compose.yml`/`.env` is intentionally weak and checked into a repo people will read; a real (even if free-tier) deployment reachable over the public internet shouldn't sign tokens with it.
- **Both Cloud Run services deployed with `--allow-unauthenticated`** — appropriate for a demo link (anyone with the URL can hit `/staff/create`/`/staff/login`, which the app itself already leaves unauthenticated — see `api-spec.md` Assumption 1), but worth being explicit this is a platform-level gate distinct from the app's own JWT auth, which still fully applies to `/patient/search` regardless.
- **Caught a real leak-in-waiting: the first draft of `deploy-gcp.sh` had `NEON_DATABASE_URL` (with the real Neon password) as a variable to be edited directly in the script.** That script is meant to be committed — the moment someone filled it in and ran `git add`, the DB password would land in git history, and this project is headed for a public GitHub repo. Fixed by moving all config/secrets into a separate, gitignored file (`deployments/gcp.env`) that the script sources at runtime, with `deployments/gcp.env.example` as the tracked template. The script itself now contains no real values ever, at any point in its lifecycle — safe to commit before, during, and after being filled in and used.
- **`docker-compose.yml`'s hardcoded `POSTGRES_PASSWORD`/`JWT_SECRET` are a different, lower-severity thing than the point above — worth being precise about why, rather than treating every hardcoded-looking value the same.** They don't protect anything real: that Postgres instance only exists inside `docker-compose`'s own Docker network while it's running, never reachable from the internet, so the value itself carries no risk regardless of who reads it in the repo. Left them as literal defaults for a long time specifically so `docker compose up` keeps working with zero setup, which the project has valued throughout (see README). Still moved them to `${VAR:-default}` interpolation reading from a gitignored `deployments/.env` (with `deployments/env.example` as the tracked template) — not because the old version was unsafe, but because "hardcoded-looking secret in a public repo" is worth avoiding on sight even when the actual risk is near zero, and the override costs nothing: `docker compose config` resolves identically with no `.env` present, confirmed.
- **A real bug found while actually using `gcp.env` for the first time: an unquoted `&` in `NEON_DATABASE_URL` silently dropped the whole value.** `deploy-gcp.sh` sources `gcp.env` as an actual shell script (`source gcp.env`), not as inert key-value data — so `VAR=postgres://...?sslmode=require&channel_binding=require` (Neon's own copy-pasteable connection strings include that `&channel_binding=require` suffix) gets parsed by bash as *two* things: `VAR=postgres://...` run as a backgrounded assignment (which happens in a subshell and never reaches the parent script) followed by a separate, pointless `channel_binding=require` assignment. Net effect: `NEON_DATABASE_URL` silently never got set at all, surfacing later as `: NEON_DATABASE_URL: parameter null or not set` — confusing, since the file clearly had a value in it. Fixed by quoting the value (`NEON_DATABASE_URL="postgres://...&channel_binding=require"`), which makes the `&` a literal character instead of a shell background-job operator, and updated `gcp.env.example` to show the value quoted from the start with a comment explaining why, so the next person filling this in from a Neon-generated URL doesn't hit the same thing.
